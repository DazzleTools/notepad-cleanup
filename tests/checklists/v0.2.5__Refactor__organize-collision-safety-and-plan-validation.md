# Human Test Checklist -- Organize Collision Safety & Plan Validation

**Version:** v0.2.5 (unreleased)
**Type:** Refactor / Bugfix -- `organize` destination handling
**Automated coverage:** `tests/test_organize_collisions.py` (14 tests)

## What changed and why a human must check it

`execute_plan()` used to compute `dest_path = cat_dir / new_name` with no existence
check and copy with `shutil.copy2()`, which overwrites. Two plan entries sharing
`category` + `new_name` produced **one** file on disk while the summary reported
**two** organized successfully -- silent data loss with a success report.

Now colliding destinations are de-collided (`name.txt` -> `name-2.txt`) and every
rename is reported. A new `validate_plan()` refuses to organize a plan that would
lose or mis-file content.

**What the mocks cannot cover:**
- Whether `_summary.md` actually *reads* clearly to a human deciding what happened
- Real Claude CLI output (the automated tests use hand-written plans)
- Windows case-insensitive filename collisions (`Notes.txt` vs `notes.txt`)
- Whether the CLI's refusal message is actionable or just alarming
- Interaction with real dedup symlinks in `organized/`
- Re-run idempotency against a real previously-organized folder

## Section 2 -- Real collision, real output

Create a small extraction folder by hand:

```
mkdir -p /tmp/nc-test/window01
printf 'milk, eggs, bread'        > /tmp/nc-test/window01/tab01.txt
printf 'hammer, nails, wood glue' > /tmp/nc-test/window01/tab02.txt
```

Then in Python:

```python
from notepad_cleanup import organizer
plan = [
  {"source":"window01/tab01.txt","category":"personal-notes",
   "new_name":"shopping-list.txt","reason":"groceries"},
  {"source":"window01/tab02.txt","category":"personal-notes",
   "new_name":"shopping-list.txt","reason":"hardware"},
]
print(organizer.validate_plan(plan, "/tmp/nc-test"))
print(organizer.execute_plan(plan, "/tmp/nc-test")[1])
```

- [ ] `validate_plan` reports one `duplicate destination (will be auto-renamed)` line
- [ ] `stats` shows `{'copied': 2, ..., 'renamed': 1}`
- [ ] **Two** files exist: `shopping-list.txt` AND `shopping-list-2.txt`
- [ ] `shopping-list.txt` contains the **groceries** (first entry keeps the name)
- [ ] `shopping-list-2.txt` contains the **hardware** list
- [ ] `organized/_summary.md` contains a `## Renamed to avoid collisions` section
      naming both the old and new path
- [ ] **Judgement call:** reading only `_summary.md`, is it obvious *which* file
      got renamed and *why*? If not, the wording needs work.

## Section 3 -- Cross-category names must NOT be renamed

Same filename in two different categories is legitimate.

- [ ] Build a plan with `readme.txt` in both `code-snippets` and `personal-notes`
- [ ] Both land as `readme.txt` in their own folders -- **no** `-2` suffix anywhere
- [ ] `stats['renamed'] == 0`

---

## Section 4 -- Windows case-insensitivity (mocks miss this)

- [ ] Plan with `Notes.txt` and `notes.txt` in the **same** category
- [ ] On Windows these collide on disk. Confirm **two** distinct files result
      (one renamed) rather than one file silently winning
- [ ] Confirm no crash and the rename is reported

**Expected:** de-collision keys on the lowercased path, so this is treated as a
collision. If two files appear with names differing only in case, the fix is
incomplete on Windows.

---

## Section 5 -- Plan validation refuses bad plans

- [ ] Plan referencing a nonexistent source (`window99/tab99.txt`):
      `validate_plan` reports it, and `organize` **refuses** with a red message
- [ ] Plan with the same source twice: reported as `duplicate source`
- [ ] `validate_plan(plan, folder, expected_sources=[...])` with one file omitted
      reports `missing from plan: <that file>`
- [ ] **Judgement call:** is the refusal message actionable? Does it tell you
      where to look (the log path) rather than just failing?

---

## Section 6 -- Re-run idempotency (regression risk)

Collision tracking is intentionally scoped to a single run. Re-running must not
accumulate copies.

- [ ] Run `organize` on a folder, note the files in `organized/`
- [ ] Run `organize` again on the same folder with the same plan
- [ ] Confirm **no** `-2` / `-3` duplicates appeared -- the second run overwrote
      its own previous output, as before
- [ ] `stats['renamed'] == 0` on the second run

**This is the most important regression check in this document.** Checking the
filesystem for collisions instead of just the current run would break this.

## Why this matters beyond `organize`

The parent design ends in a `drain` step that deletes the source Sublime session
after extraction. Its entire safety argument is "verified extraction earns the
right to delete." A stage that silently overwrites files breaks that chain, so
AC-22 and AC-23 are preconditions of the drain -- not merely nice-to-have quality
fixes.
